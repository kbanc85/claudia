# v1.67 "Is OKF" Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Make Google's Open Knowledge Format (OKF) the mandatory authoring standard for every knowledge file Claudia writes: OKF frontmatter on all authored knowledge files, index.md maintenance as standard behavior, an additive migration for existing installs, lenient reads.

**Architecture:** Three layers. (1) A NEW shared schema: `memory-daemon/claudia_memory/okf.py` (constants, frontmatter build/parse, spec-version marker) plus `docs/okf-conventions.md` (the canonical conventions doc that skills cite). Nothing shared exists today; this is the keystone. (2) Template layer: prose edits adding OKF frontmatter to the embedded templates in `structure-generator.md` and friends, collapsing duplicate templates, and specifying index.md maintenance. (3) Daemon layer: normalize the five frontmatter builders in `vault_sync.py` through `okf.py`, plus an `okf-normalize` migration command in the admin CLI.

**Tech Stack:** Python 3 (daemon), markdown/prose (template layer), pytest. Base branch: `main` at v1.66.0 (commit adee829 or later). Branch: `feat/v1.67-is-okf`.

**Primary spec (fetch and read BEFORE coding):** https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md (v0.1 draft). Core: one required frontmatter field `type` (free string); recommended `title`, `description`, `resource`, `tags`, `timestamp` (ISO 8601); consumers MUST tolerate unknown fields; reserved per-directory `index.md` (listing) and `log.md` (history); concept ID = path minus `.md`; links are plain markdown.

**Design decisions (locked by Kamil 2026-07-09, do not relitigate):**
- Mandatory applies to what Claudia WRITES. Reads stay lenient (never validate-and-reject user files).
- Migration is additive-only and reversible: add frontmatter, never touch body content, dry-run by default, backup before write.
- All OKF field logic lives in `okf.py` with `OKF_SPEC_VERSION = "0.1"`; the spec is a draft and will churn, so exactly one module absorbs it.
- Claudia-specific fields (`claudia_id`, `sync_hash`, `importance`, `cssclasses`, wiki provenance fields) are KEPT as extension fields alongside the OKF core (the spec explicitly permits unknown fields). Nothing is deleted, fields are added/normalized.
- Reconciliations (recon C3): `title` is the canonical display-name key (vault `name` and wiki `entity` stay but `title` is added); `type` is canonical (wiki `entity_type` stays but `type` is added); `timestamp` is the canonical last-meaningful-change key.

## Task 2: The keystone — `okf.py` (TDD)

**Files:** Create `memory-daemon/claudia_memory/okf.py`; test `memory-daemon/tests/test_okf.py`.

API (write failing tests first, then implement):
- `OKF_SPEC_VERSION = "0.1"`
- `build_frontmatter(type, title=None, description=None, tags=None, timestamp=None, resource=None, extra=None) -> str`: emits a `---` YAML block, `type` first, only-non-empty fields, `extra` dict appended after OKF core fields, deterministic field order (stable for sync hashing), values YAML-escaped (colons, quotes).
- `parse_frontmatter(text) -> (dict, body)`: lenient; returns ({}, text) when no block; tolerates unknown fields; never raises on malformed YAML (returns best-effort or empty dict).
- `normalize(existing: dict, type, title, timestamp) -> dict`: given an existing frontmatter dict, ADD missing OKF core fields without touching unknown/extension fields.
- `TYPE_VOCABULARY`: the house `type` strings (person, project, organization, concept, location, context, meeting, deliverable, pattern, reflection, session-log, moc, wiki-page, commitment-ledger). Free-string per spec, but Claudia writes from this list.

Tests: build round-trips through parse; extension fields survive normalize; malformed YAML does not raise; deterministic ordering; escaping. Commit: `feat(okf): shared OKF schema module (spec v0.1)`.

## Task 8: Migration — `okf-normalize` admin command (TDD)

**Files:** Modify `memory-daemon/claudia_memory/__main__.py`; test `memory-daemon/tests/test_okf_normalize.py`.

`claudia-memory --okf-normalize --project-dir <install path> [--apply]`:
- Walks the install's knowledge dirs (`people/`, `projects/`, `context/`, plus `clients/`, `pipeline/` etc. when present), skipping `.claude/`, `workspaces/_templates`, non-md files.
- For each file WITHOUT conformant frontmatter: infer `type` from directory (people→person, projects→project, context→context, else `concept`), `title` from the first `# heading` or filename, `timestamp` from file mtime; ADD frontmatter via `okf.normalize`; body untouched byte-for-byte.
- Dry-run by default (prints the would-change list, per `--migrate-vault-para --preview` precedent); `--apply` copies each file to a timestamped backup dir under `~/.claudia/backups/okf-normalize-<date>/` before writing (per `--backfill-entities` precedent).
- Generates/updates `index.md` per directory per conventions doc; idempotent (second run = zero changes).
- Tests (temp dirs only): dry-run mutates nothing; apply adds frontmatter and preserves bodies exactly; idempotency; backup exists; files WITH existing frontmatter get missing core fields added, nothing removed.

Commit: `feat(cli): okf-normalize migration (additive, dry-run default, backup-first)`.
